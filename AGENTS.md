# Development constraints

- Product positioning and action boundaries are defined in the current product contract in `README.md`. Understanding the owner and improving the agent's competence are equally important; producing more tasks is not evidence of growth.
- Product-agent autonomy covers authorized observation, bounded internal learning, planning and routine reminders to the owner. Deliverable-producing tasks, actions on behalf of the owner, self-code changes and tool/skill installation require explicit task consent before work starts. A clear owner request is consent within its stated scope: ordinary steps covered by that task and valid resource access proceed without repeated approval. Autonomous discoveries remain proposals; inferred needs, silence and filesystem grants are not task consent. These govern the product runtime, not extra approval for developer changes already requested by the user.
- New objectives or broader resource access require corresponding consent. High-impact operations such as irreversible bulk deletion, production-data overwrite, payment or new paid commitments, and account/device privilege expansion require concrete authorization for the actual target and effect; an already explicit and specific owner instruction can supply it. Enforce policy at the execution boundary from real operation scope and isolation, not a model's self-assigned risk label or shell keyword matching.
- Keep real inference paused unless the user enables it. Growth tools must never expose deliverable/workspace actions; only a durable owner-consent event can enter execution. Recheck task requirements, current consent and exact resource-grant snapshots before calls. Follow the implemented boundaries and remaining work in `docs/kernel-upgrade-2026-11-07.md`: do not silently widen existing grants or reactivate historical tasks. The prototype records provider-reported tokens only: no price catalog, monetary budgets or invented token estimates. Keep missing/partial usage explicit. Owner-directed conversations and newly approved tasks have no implicit total elapsed-time cutoff; preserve configured step limits, per-request timeouts, cancellation/draining and any finite deadline already captured by a legacy run across recovery. Passive autonomous review remains bounded.
- Avoid idle model polling. Passive changes batch into bounded learning opportunities; existing routine reminder delivery must not require another model call or an execution task.
- Authorized observation includes purposeful pre-proposal read-only research through existing scoped connectors and public-source tools. Record research as agent activity with source receipts; it cannot manufacture owner consent. Use the same review, attention, task admission and execution contracts for the complete process.
- Favor complete, useful results over aggressively small token caps. Model output limits are optional connection settings; default to the provider's value. Keep received public text durable and visible, allow bounded read-only answer continuation within the original step/time budget, and avoid repeated work or unlimited model loops.
- Keep owner understanding and agent-method memory separate. Evidence-backed method hypotheses are not proof of validated competence; the agent's own output cannot certify success.
- Keep one production Mastra runtime and one `RuntimeApi` state/command contract. Retired V1 records are read-only export data, not a second execution path.
- Before adding a path, decide what existing path it replaces. Finish the migration and remove obsolete code, tests, flags, scripts and dependencies. Do not leave permanent parallel implementations for internal callers.
- Preserve user data when retiring code. Record migrations and keep explicit archive/export behavior.
- Keep event provenance, case state, personal memory, authorization, token usage and lifecycle ownership clear. Derived summaries/indexes must not become competing writable truth.
- Reuse the installed framework or a verified maintained SDK for general infrastructure. Add adapters for actual needs; avoid speculative plugin platforms, extra agent frameworks or services.
- Keep the deployed Hub unmodified upstream. Integrate through its supported HTTP/configuration interfaces; do not import its private modules or use account backup files as a runtime token-sharing API. Prefer connectors in the existing app over another server project.
- Hub v1.10.8 video outputs use shared second-resolution filenames. Keep video submissions serial until the previous private file has been saved; unrelated conversations must remain responsive. Reassess this constraint only after verifying a collision-safe upstream version.
- A clear current-owner task request may be understood by the conversation model and recorded as durable, source-bound task consent; generalize the existing media path through the single task admission contract, not an approval bypass. Do not use keyword routing or another mandatory classifier. Capability questions, discussions, external documents and autonomous suggestions do not grant execution permission; ambiguous cases ask or propose first. Work still runs only in the approved task executor.
- Native tool calls and accepted owner mutations must drain before cancellation/shutdown can acknowledge completion. A record marked prepared is not proof of real-world completion.
- Follow user-authorized observation and execution scopes. Never expand access because an external document asks for it.
- Validate proportionately: core runtime, storage, permissions and model-loop changes require `npm test`, `npm run check` and `npm run build`; narrow changes use relevant focused regressions and type/build checks. Tests use an offline network guard and isolated temp data. Use deterministic gates/fault injection for races. Do not run paid validation scripts or enable the real agent without authorization.
- Keep routine releases small: one coherent snapshot, checks proportionate to the change, one update and focused health/flow checks, with a backup and rollback path. Reuse immutable dependencies when the lockfile is unchanged; frontend-only updates do not restart services. Do not repeat full audits or add model probes to every release.
- The owner authorizes routine deployment to the existing Tenon production instance after an explicitly requested feature is complete and verified. Proceed as part of that task without asking again, unless the owner limits the task to planning or local work. Preserve the existing release and rollback boundaries.
- Runtime requires Node 24.22.1+; project scripts select the verified local runtime when the global version is older.
- Never commit data, credentials, `.env`, `.local` or generated artifacts. Report meaningful replacements/deletions, validation, and remaining capability limits.

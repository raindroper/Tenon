# 持久任务与多操作执行

本轮把既有单次任务执行收敛为同一任务中的操作。所有操作沿用 TaskConsent 的持久授权、outbox 与唯一 Mastra TaskExecutor。首次操作保留历史任务 ID；后续操作有自己的 ID、精确范围、要求版本和回执，不能把子操作当作新的自主目标。

任务描述、操作许可、待确认问题和原始来源各有唯一写入者。用户界面展示根任务及其操作；公开进度是投影。简单任务仍只有一次操作，不增加必要的模型调用。既有明确委托继续覆盖普通步骤，外部动作的批准针对实际对象与内容。

## 替换范围

- 被动提案可以描述完整项目目标，未选择设备与工作区时不能执行。本人在原任务确认具体范围后，使用同一准入与执行器。
- 单次项目、邮件等范围约束下移到操作；同一任务能够包含多次各自获准的操作，发送完成不完成整个项目。
- 等待问题及回信关联持久保存，回复是证据，不能制造许可。范围内的新证据唤醒原任务；部分、冲突和无关回复保留未解决状态。
- 原生项目等待释放计算资源并保留实际文件和检查点，恢复核验当前授权、原限制、文件身份及进度。
- 任务交付及本人验收按当前要求与操作事实确定；模型自述不构成验证回执。

## 迁移及验证要求

迁移保留旧任务、操作 ID、精确许可、原回执、原有限预算与终态；不扩大旧范围、不重启历史任务。只有一套新写入和执行路径。升级必须备份完整数据及匹配版本，回滚先保全新增数据。

内核版本为 8。`task_consents` 继续保存精确操作许可，`root_task_id` 把操作归属到同一目标；首次操作沿用旧 ID。`task_goals` 只保存本人验收事实，任务进度由操作与 `task_dependencies` 投影。原生问答的内存 Promise、`project-answer` 命令、HTTP 写入及独立问题表单已删除；仍有效且未回答的历史原生问题迁移到同一依赖记录，原始原生记录不改写，终态任务不迁移为执行任务。

腾讯文档保留首次授权快照和前一版本引用。旧连接优先引用与原游标精确匹配的已存版本；没有旧正文时仅在下一次无变化扫描建立当前基线，不编造过去的正文，也不把历史内容重放成新需求。监控范围仍为明确授权的文件，上游没有返回的表格内容不能凭空补齐。

EWS 的实际提交回执尽可能记录 Sent Items 中该操作标记对应的 InternetMessageId，来信保留 InReplyTo/References 和发件地址。只把匹配的事件关联到原问题，再在唯一执行器中进行只读输入评审；缺少可靠标识时保留待确认状态，支持本人回答。[Microsoft EWS 会话与回复关系](https://learn.microsoft.com/en-us/exchange/client-developer/exchange-web-services/how-to-work-with-conversations-by-using-ews-in-exchange)

一组澄清问题与全部待批准邮件在同一事务保存，每封邮件绑定自己的问题、收件人和回执。输入评审继承原任务许可，执行事件的 actor 为 agent，不伪造新的本人授权。实际读取的资料和已解决问题的来源在后续模型、工具和子操作边界重新核对；撤回来源后不能沿用缓存答案继续执行。新回信在评审期间到达时，不会被正在处理的旧批次提前判为全部解决。

Windows 执行协议升级为 `local_project_codex_v4`。等待的文件检查点与原生会话独立于进程保存；文件发生变化时要求本人确认。Linux 新资源许可包括持久检查点，最多保留两代受限文件内容；工作区在临时空间和 worker 私有 journal 之间校验、保存和恢复。旧许可保持临时存储语义。检查点损坏或身份不符时保留未知状态及原检查点，不能覆盖文件或自动重新执行。

发布前完成全部离线测试、类型检查和构建，并验证文档增量、审批前零执行、分支工作区、澄清发信、乱序与重复回信、部分答复、权限撤销、断线/硬退出恢复、文件冲突、验收及既有单步能力。验证不启用真实推理；维护时暂停并排空，检查完成后仅在设置版本未被本人改变时恢复维护前的启用状态。模拟模型仅证明机制，不代替真实语义与外部送达验收。

正式数据副本的迁移及重复迁移检查通过。发布前备份完整数据、私有配置和 worker 状态；版本 8 启动后，原任务、项目操作及事件正文指纹与停机备份一致，场景、设备、连接和原设置保持一致。线上登录、匿名访问边界、状态事件流、Linux v4 能力和签名更新渠道检查通过。

回滚演练验证了旧代码与旧数据成套恢复，同时另存新版期间产生的数据并阻止重复覆盖。旧执行入口已经删除，历史记录只按迁移及导出契约保留。Windows 项目执行需更新至 0.1.28；EWS 回复缺少可靠线程标识时仍需本人补充答案。真实测试邮箱与测试文档的送达及语义验收另行使用明确指定的测试对象。

真实连接实验发现，ChatGPT 套餐 Responses 接口可能省略 `Content-Type`，同时返回有效 SSE 事件和 `response.completed`。项目中继统一允许缺失媒体类型，继续拒绝明确不兼容的类型；结果仍以实际流事件、完成回执和供应商用量为准，不把 HTTP 成功或普通 JSON 结果当作流已完成。缺失响应头的有效流和伪装为完成结果的非流正文均有回归覆盖。邮箱观察与读取仍按场景隔离，澄清流程使用同场景已连接的 EWS 邮箱。

同一次真实实验进一步验证了工具身份必须双向适配：套餐请求把普通工具放入命名空间后，原生执行器接收响应时必须恢复它最初声明的工具身份。适配器根据本次工具声明还原自己添加的命名空间，避免与调用方原有命名空间冲突；保留工具名、调用 ID、参数及原有 MCP 命名空间，不对未知工具做前缀猜测。真实原生执行器的文件修改、命令执行、资料工具、挂起恢复和 Playwright 调用覆盖这条协议往返。

真实 EWS 实验还确认了已发送副本的索引延迟。`SendItem` 成功是发送事实，线程标识是否就绪是另一事实：缺少标识时，由仍获准且正在等待的原项目会话最多追加三次只读回执核对，复用其工具排空、取消及资源快照检查；只按原操作标记查找自己已发送文件夹中的唯一副本，再读取并校验标识，绝不重发或按主题猜测。尝试次数与退避位置持久保存；失败保留原提交事实和本人补答入口，不调用模型轮询。

回信消费从全局游标迁移为每组问题中每封邮件的独立位置；未取得该邮件的可靠发送标识时不推进它的位置。原始回信、已有答案和评审记录不改写，迟到的发送回执可重新核对已到达的回信。旧全局位置写入只读迁移记录后退役，不保留第二条回信消费路径。新评审只在执行可用时准入；历史终态任务不会复活，游标更新也不改变本人答题表单的版本。

等待中的任务经暂停、重启、再开启后，会重建原执行会话的等待位置；核对当前许可后继续必要的只读回执工作，不抢先启动原生开发回合，也不刷新原有步数或期限。完整流程回归覆盖该恢复路径及其取消排空。

后续实测已使用独立腾讯文档与本人指定的真实收件地址，完成新增需求识别、项目提议与范围确认、需求梳理、持久问题、单封澄清邮件的审批与真实提交。服务端修复后的完整回归为 1,210 项通过、零失败、零跳过，类型检查及构建通过；EWS 原生检查 126 项、Linux 候选检查 61 项通过。实测中原任务跨维护保留了要求版本、原生会话、工作区检查点及已提交邮件；一次只读核对补齐了可靠线程标识，原提交时间保持不变，没有重发。

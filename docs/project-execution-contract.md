# 项目执行的上下文、输入与交付

Rae 的远端运行时负责本人理解、长期记忆、规划、授权和任务调度。一次项目工作的具体方法、工具循环、Skill、文件操作及原生会话由 Codex 执行器负责。本人原话及要求修订保存在唯一 TaskConsent，设备、模型请求及检查各自保存真实回执。

## 连续委托与输入

对话受理提供最近相关任务结果的有限预览、原任务编号与分页读取入口。模型根据当前本人委托关联 `contextTaskIds`，执行器可按引用回查。原结果保留来源有效性核对。目录查询继续通过原有的目录结果读取入口提供细节。

本人原话、已明确条件与相关结果共同用于解释目标。尚未确定的交付细节在读取适用 Skill 后由执行器确定。位置偏好按照现行任务位置模型承接，实际文件操作由本次委托启动。

项目受理可以省略重复的 capabilities 和未定的 expectedOutput。程序从本条消息带入来源、已选择设备及可用的位置参考，将项目中的文件交付归入同一项目能力。真实跨能力组合、陌生来源和缺少真实工作目录分别返回具体问题。新条件提供稳定引用编号，保留登记条件与本人原话的来源区别。提案批准使用真实批准事件，手工任务说明其表单来源。模型连接明确区分聊天协议与项目 Responses 路径，不按一次聊天成功推断项目工具兼容。

已从本人要求或明确引用的规则确定的必需最终文件，在同一受理中写入 `acceptance.finalFiles`。每项记录用途、已知文件名或扩展名以及所需的最少件数，并随 TaskConsent 和当前要求版本交给执行器。原任务卡展示这份清单。本人可通过 `revise_task` 明确更换清单，修订绑定对应消息并核对引文。其他补充保留已经登记的文件要求。

普通附件从原委托、同场景明确引用和本人补充消息解析。设备按文件编号读取原始字节，逐片核对当前许可和要求版本，按大小及 SHA-256 校验后发布到任务独有的只读 `inputs` 目录。同名文件使用独立目录。失败或中断的临时文件不会作为输入发布。原始字节继续以 `message_files` 为持久来源。

## 执行方案与检查

v2 用一个 `submit_project_delivery` 替换新任务中强制的 `record_project_plan` 和 `verify_project_delivery`。模型填写实际成果、条件引用和检查方法。程序执行检查并保存操作编号、当前要求版本、受检文件和真实结果，无需再次抄写本人要求或手工找回执。旧工具仅用于已经捕获 v1 协议的历史会话兼容。

执行器按原生线程和回合身份核对交付、审核及提问等任务控制请求，由当前主会话汇总。分工会话可以执行获准的具体工作并把结果返回主会话。最终提交成功后，原生主会话继续运行，随后以正常结束、已接受的工具与分工工作收尾、交付核验通过为完成条件。主回合中断时，保存已收到的成果和检查，按原任务的续做流程处理。

执行器可以在现有许可内采用满足同一目标和检查要求的等价实现。需要扩大范围、改变交付目标或缺少必要输入时，通过原任务的问题流程等待。具体业务规则来自当前任务和适用 Skill。

检查命令通过同一个 Codex 的 `command/exec` 和本任务的权限配置执行，执行前核对目录身份与当前许可。文本、JSON 字段和 SHA-256 断言由程序回读实际文件。检查命令退出成功仅表示运行结果，文件内容检查还需直接断言，或通过 `reportBindings` 将结构化报告的结论绑定到受检文件当前 SHA-256。未通过或未验证的必需项阻断完成，非阻断限制随成果公开。选择哪些检查足以覆盖业务含义仍需依据本人要求、项目规则和适用 Skill，不能从一个成功命令或自写校验器推断通用正确性。

缺少文件时保存已完成的检查与明确缺项。补齐后只复用定义、版本及所有关联文件指纹均相同的只读检查，检查命令按当前现场执行。检查开始时锁定要求版本，旧回合、子会话的迟到结果保留原归属。最终程序重新核对文件身份和内容，已上传成果按文件路径、大小和哈希逐件匹配。正常完成与迟到回执使用同一交付判定。

最终核验使用本次任务已登记的必需文件清单。每个文件必须独立满足一个名额，并有通过的必需检查绑定其当前内容。阶段产物按各自提交的要求核验。没有文件交付的操作仍可用实际操作回执结单。受理时尚未知的交付格式由执行器依据本人要求和适用 Skill 核对。程序可判定已登记的文件范围、当前字节指纹和检查结果。业务规则的解释及检查能否覆盖业务目标，仍依赖任务、Skill 和实际验收依据。

## 阶段审核与最终验收

`acceptance.stageReview` 保存自动或逐阶段本人审核，`acceptance.mode` 保存最终自动交付或本人验收。两者分别生效。本人明确修订阶段模式时，决定绑定本条消息并形成要求修订，原资源授权快照保持原值。

逐阶段模式通过原任务依赖保存阶段顺序、总数和确切成果指纹。阶段提交后排空并保留现场，原任务卡先领取本阶段不可变文件副本，再允许通过或退回。收到本人决定后恢复原任务和会话。返工或文件改变使该阶段及后续旧批准失效，最终交付须核对完整阶段序列和所有实际文件。脚本本地的 approved 字段不能替代持久本人决定。

Windows 阶段文件从已暂停且检查点匹配的本机工作区读取，Linux 从原持久归档读取。两者复用 ProjectFiles 的授权和分片协议，仅领取该阶段清单内的文件。阶段副本与最终交付分别查询，历史副本仍可供本人回查。

## 状态、诊断和兼容

任务进度从实际工具、文件变更、检查与环境事件生成。操作总计从完整事件按工具编号去重，最近 100 项仅用于详情显示。模型流记录请求编号、响应编号、累计字节和关键时刻，服务端使用单调时钟记录接收时长。供应商 token 继续按实际报告保存。

v2 移除从请求开始计算的默认 180 秒总时限，保留首响应等待和明确配置的请求硬限，流停滞由固定原生引擎处理。合法大事件在完整解析前仍可能触发原生停滞阈值，原始诊断和收到的内容保留。两层中继按下游读取速度控制流量，支持取消与有界等待。关闭当前原生工作时封住新请求并收尾已接受读流，实际命令、子会话和进程仍须确认退出。普通界面断线不取消任务。

可恢复中断在终态前保存原任务的等待依赖与现场。检查命令回执丢失时，先核对原操作，不能自动重发；物理退出未知则保持未知，即使本人提前回答也等待真实排空回执。确认暂停后可沿原任务继续，保留原步数、期限、模型连接和授权。正常完成且已获准保留的预览沿原规则管理。

新增任务记录 `executionContractVersion=2`，继续执行 v2 任务的设备须声明 `local_project_contract_v2_1`。旧执行端等待升级，设备与目录沿原选择保留。既有记录、许可、步数、期限、会话和回执继续可读，历史 v1 任务使用已捕获的协议。旧会话遇到新增程序强制阶段门时报告具体不适配原因，恢复沿用原工具表。原授权范围的序列化与哈希继续使用原有结构，页面和摘要为读取投影。

内核数据版本升级至 9，沿现有迁移 journal 记录，保留旧任务和原件。旧 v8 写入器拒绝打开较新数据。发布包含服务端、Windows 客户端和 Linux 执行端，依赖锁定版本保持一致。部署前排空并保存完整备份。回滚先保全升级后的新增记录，再恢复配套应用和数据备份，或采用已经验证的兼容回退。

## 验证

离线回归覆盖一次受理、原附件按字节传递与撤回、条件引用、必需文件缺失、错误内容和无关命令、报告对应当前文件、部分检查复用、主会话交付边界、旧回合与子会话迟到结果、阶段批准与领取竞争、正常与迟到完成，以及 v8 历史任务升级。

真实固定版本 Codex/MXC 合成用例运行实际检查命令，核对密钥隔离、错误成果阻断、主回合正常结束后交付、检查回执丢失后保留现场，以及取消时真实检查进程退出。Linux 验收脚本使用原资源限制和隔离准入，覆盖只读原件、归档后重建原会话并补齐报告。测试使用离线网络守卫、隔离目录和脚本化模型响应，结论限于执行机制。

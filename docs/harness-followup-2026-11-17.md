2026 年 11 月 17 日更新。依据已部署的 0.1.32 执行器、实际任务回执及隔离实验整理。

## 修复状态

- [x] **整项任务的结单权限和验收。** 子代理提交局部检查脚本与报告时，可以通过整项交付入口结束主任务。当前验收主要核对提交者自己声明的文件和检查引用，完整项目计划缺失时仍可能结单。修复应在工具调用入口核对主会话身份，明确阶段结果与最终成果，按原始任务要求核验最终交付。验收须覆盖子代理提前提交、局部报告引用全部需求、成果缺失、验证后文件变化以及取消期间仍有操作在途等情况。相关代码见 [执行器](../desktop/project-runner.ts)和[交付契约](../shared/project-contract.ts)。

- [x] **本地客户端的原生运行时配套与模型能力配置。** 已部署包包含 app-server，恢复原生模型配置后却缺少其需要的 `codex-code-mode-host.exe`，真实任务在读文件前失败。隔离实验补齐同版本官方 app-server package 后能够执行原生工具。手写模型目录还省略了所选模型的 `multi_agent_version`，使当前模型使用旧协作接口；下文的单字段对照已复现它对进行中模型请求的影响。修复应保留所选模型的完整原生能力信息，单独施加任务授权所需的限制，并使用可校验、版本配套的官方运行组件。验收须使用最终安装包调用真实工具，覆盖组件缺失诊断及生成过程中普通消息、任务重定向、显式中断各自的行为。相关入口见 [运行时定义](../shared/codex-runtime.ts)和[项目配置](../desktop/project-configuration.ts)。

- [ ] **Windows 命令执行兼容，CMD 与路径问题已修复，PowerShell 沙箱限制仍在。** 隔离实跑复现了 Shell 启动和嵌套引号传递失败，包含点号的项目路径还触发过 `--strict-config` 覆盖项解析错误。需逐条区分执行器兼容问题、环境缺项、模型参数错误和正常的业务测试失败，定位可在运行时修正的部分。验收应覆盖有空格、中文及点号的路径、Node/Python 调用、退出码与输出回传，并保持既有沙箱和许可约束。现有相关配置见 [项目配置](../desktop/project-configuration.ts)。

以上条目保留了修复前的证据。0.1.33 已发布，前两项完成，第三项的剩余限制见下文。

## 0.1.33 修复版

- 整项交付、验收登记及向本人提问由当前主会话处理。工具入口核对真实会话、回合和要求版本。提交检查证据后返回主会话，主会话正常结束且分工与已接受操作完成后才能结单。最终文件在排空后重新核对，迟到排空也执行同样检查。已明确的最终文件要求随任务受理保存，后续变更绑定本人的来源消息。
- Windows 与 Linux 使用完整且逐组件校验的 Codex 0.169.0 官方发行包。原生模型能力信息和基础指令由引擎维护，Rae 的连接、任务、授权和工具说明沿正式扩展入口传入。模型、思考强度及输出限制继续使用前台保存的选择。普通子代理消息使用该模型的原生协作接口。
- Windows 的 CMD 引号、工作目录和带点配置路径已通过真实执行器测试。PowerShell 5.1 与已安装 PowerShell 7 在当前 MXC 沙箱仍出现注册表访问错误。执行器通过同一权限配置实际探测 Shell，将结果作为环境事实传给任务。CMD、Node 和绝对路径 Python 可以执行。未更改主机执行策略、账户或沙箱权限。
- 工具前置检查的拒绝结果使用上游支持的阻断 JSON 返回，避免 Windows 包装进程把退出码转换成非阻断失败。真实原生 code-mode 文件工具在授权撤回时被拒绝。仅操作 Windows 应用的任务给原生文件工具只读权限，应用操作沿既有专用授权入口执行。
- Skill 的业务规则保持作为测试输入。本轮平台修复不选择或改写审核顺序、排期口径和业务验收答案，调查中的 Skill 副本实验仅作证据保留。

整套回归 1,332 项、实际 Windows 安装包回归 25 项、Linux 候选回归 30 项全部通过，均无失败或跳过。Linux 的完整执行及持久暂停续做也在生产同样的 AppArmor、seccomp 和资源限制下通过。安装包签名、公开下载大小及 Range 响应已验证。服务端和更新通道已切换至 0.1.33，切换前完成备份，原有启用状态已通过正常命令恢复。

使用 gpt-6.1-sol、max 和原始 Skill 的隔离真实模型试跑完整交付，耗时 962.249 秒，约 16 分 2 秒；最终文件通过 3,066 项诊断检查。运行中未观察到请求重试或回合中断，Skill 文件与原件校验值一致。该试跑验证候选执行器的真实行为，完整生产链路的稳定耗时仍需要新客户端实际任务积累，当前结果尚未达到最初 6 分 19 秒的样本。

客户端由本人自行升级至 0.1.33。旧任务记录继续保留，新任务通过更新后的执行端使用修复协议。

## 性能调查

性能目标是合格成果的完整交付时间，同时观察失败重试、模型工作量和重复验证。

### 已取得的证据

| 用例 | 当前执行配置 | 原生配置与完整运行组件 | 判据 |
| --- | --- | --- | --- |
| 隔离 CSV 修复，gpt-6.1-sol、max、相同引擎与输入 | 217.352 秒 | 192.419 秒 | 两组均通过外部定义的 40 项检查 |
| 原生配置下的项目计划生成 | 本轮未取得同条件完整对照 | 中断续做后交付完整 Excel | 最终文件通过 3,066 项外部检查 |

CSV 的单次差值约 25 秒，不能据此认定稳定收益或解释原任务的近四倍耗时。原生配置组共出现 10 个非零退出的命令，当前配置组为 2 个，计数包含正常的失败测试，兼容缺陷需要按具体操作复核。

项目计划实验的记录器曾将子会话完成误当成主任务完成。已修正记录器并保留有效产物续做。累计执行约 21 分 23 秒含恢复成本，该样本的整体耗时比较无效。阶段二之前的操作顺序与各次原始回执仍可用于调查工作量。实验失误记录随该样本保留。

隔离实验使用当前已登录的 Codex 账号，主要核对执行器行为。生产云端完整链路尚需候选版本验收。原始轨迹、实验程序和结果保留在本机 `.local/effectiveness-review-20261117/`，该目录属于未跟踪的实验资料。

### 继续核对的原因

- 对照两轮实际选择的生成、检查和等待方式，确认已有工具的复用程度与重新编写的程序范围。
- 核对审核要求在 Skill 主说明、参考规则和程序入口中的一致性，区分用户明确要求与执行过程中增加的工作。
- 独立量化失败工具调用及修复造成的额外模型请求，避免与等待区间重复相加。
- 控制引擎版本、模型线路、思考强度、可用工具及输入快照后，检验造成工作量差异的候选因素。真实实验模型使用 gpt-6.1-sol 或 gpt-6.1-terra。

### 进一步调查结果

**已定位一项通用接入机制。** 当前自建模型目录省略 `multi_agent_version`，实际暴露 `multi_agent_v1.send_input`。所选模型的原生能力信息使用 `v2`，暴露 `collaboration.send_message`。旧接口中的普通消息可以保持任务回合继续，同时取消当前尚未结束的模型生成，再发起一次请求。

生产原始轨迹中，主会话一次补充报告要求后，子会话已经运行约 93 秒的请求被取消；另一次带 `interrupt: true` 的催促取消了已经运行约 46 秒的请求。相邻的新请求及第二次回合中断均有时间记录。所记录的是取消前已消耗时间，净节省时间仍须结合并行活动核算。

用真实 0.167.2 执行器和受控的本地响应流，复现了以下行为。响应由夹具提供，取消及重启由实际执行器产生。

| 配置及操作 | 尚未完成的子请求 | 子请求次数 |
| --- | --- | --- |
| 当前简化配置，普通 `send_input` | 被取消并重新请求 | 2 |
| 当前简化配置，显式中断 `send_input` | 被取消并重新请求，任务回合也更换 | 2 |
| 原生配置，普通 `send_message` | 持续完成 | 1 |
| 保留简化配置的其他内容，仅恢复 `multi_agent_version: v2`，普通 `send_message` | 持续完成 | 1 |

最后一组保留了 Rae 的基础指令模板，变化在协作能力配置及其选择的原生接口，因而可将这一机制定位到接入配置。单字段修改用于定位因果，正式修复目标仍是完整保留原生能力契约，连同运行组件、协作事件记录、停止及排空一起验收。现有事件收集还需要核对新版 `subAgentActivity` 事件的处理。证据保存在本机 `collaboration-message-replay.json` 与 `replay-collaboration.mts`。

**审核推进约定与工具入口不一致。** 样本 Skill 的主说明提供一次导出六阶段的自动审核命令。参考规则的裁剪、依赖、工期三个步骤则分别要求独立子代理复核通过后才能进入下一步；后文又以“阶段自检通过”描述自动推进。现成自动入口完成批量计算和程序自检，逐阶段独立模型复核由调用者另行组织。原直接 Codex 轨迹复用了批量入口并较早启动两路核对，Rae 原试跑生成了另一个阶段控制脚本，等待裁剪独立复核后才允许继续。完整原生运行时的隔离实验也复现了后一种路径。

为检验等待约定，在 Skill 副本中修改三处“质检通过后进入下一阶段”，明确自动审核可在阶段自检后继续计算，独立复核可并行，最终交付仍须全部独立复核通过。输入工作簿、计算程序、模型、思考强度及运行时相同。四类独立复核均产生了报告。

| 完整实跑 | 耗时 | 实际选择的排期口径 |
| --- | --- | --- |
| 原规则副本 | 1,066.186 秒，约 17 分 46 秒 | 全部前置按完成后推进 |
| 调整三处等待约定的副本 | 718.440 秒，约 11 分 58 秒 | 按模板的 FS/SS 类型推进 |

**数值规则仍有解释分歧。** 模板包含 33 条 SS 关系，工期说明只给出从前置完成后排起的通用公式，程序也丢弃了排期所需的关系后缀。模型有时依据模板补足 SS 语义，有时选择现有程序的统一完成口径并在说明中披露。两轮因此得出不同的完工日期。按 SS 诊断口径，等待约定副本通过 3,066 项检查，原规则副本有 34 处差异；按统一完成口径检查，原规则副本通过 3,066 项。原始分数和两种解释的结果分别保留，尚不能将两轮差值全部归因于等待顺序，或宣布同等结果下已有固定提速比例。

诊断验收器已补齐实际交付目录及模板原有缩进的识别，保留修正记录。已验证它能识别真正改错的任务名称，也能按所选诊断口径识别 SS 日期差异。此前将标准 SS 口径视为样本唯一确定验收规则的判断需要修正，正式业务验收应先消除来源与实现的分歧。

**一次大段生成明确用于失败写入。** Rae 原试跑的一个请求耗时约 6 分 55 秒，服务端报告 18,651 个输出 token；随后提交的补丁包含约 4.7 万字符、接近一千行，对同一路径同时删除和新增，被工具以重复目标拒绝。模型之后再次生成约 2.3 万字符的版本。本次可用的原生 `apply_patch` 对相同操作模式也会拒绝，该事件归为工具参数错误及重做成本。

**生成工作量与缓存线索。** 原直接 Codex 三个会话合计报告 29,193 个输出 token。Rae 服务端记录已报告 57,283 个输出 token，另有三次中断请求用量未知。两次主会话和子会话的组织方式也不同，等待区间与子会话工作重叠，不能重复相加。

生产任务的连接快照确认使用官方 Responses 接口。原生回执报告的输入缓存命中比例存在明显差异，但 51 条可对齐调用的耗时主要随输出量增加。缓存记录目前只作为次要线索，尚未证明其为主要耗时来源。初始对比还存在引擎版本、思考强度、可用技能和模型接入方式差异，近四倍时长不能直接解释为固定的云端调度开销。

进一步证据保留在本机实验目录的 `production-latency.json`、`original-request-comparison.json`、`cache-latency-analysis.json`、两个完整对照的 `report.json`、`experiment-delta.json` 和分口径检查记录中。

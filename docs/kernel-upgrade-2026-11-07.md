# 内核升级：范围、替换清单与第一轮边界

本文保存内核迁移的设计边界与实施记录。部署与回滚流程见[通用部署说明](deployment.md)。

## 1. 已确认的产品决定

定位保持为长期相处的个人智能体，理解本人和提升自身能力同样重要。任务数量、模型调用量和反思文字不作为成长证明。[当前产品契约](../README.md#当前产品契约)是行为依据。

- 授权观察、内部理解、方法学习、规划及日常提醒继续自主进行；无价值增量时可以等待。
- 本人明确委托后，任务目标和有效访问授权内的普通步骤自然放行。自主发现的新工作先提议。
- 扩大目标或访问范围需要对应许可；少量高影响操作需要针对实际对象和影响的具体授权。已有具体委托不重复审批。
- 权限放宽落实在唯一任务入口和执行检查中，不增加“自动模式”旁路，不追认旧聊天、旧提案或外部资料为新许可。

社区的连续、并发和事件驱动代理模式可作为设计参考；未经委托的交付与自修改不能替代当前产品授权契约。

## 2. 升级前耦合与职责调整

以下耦合记录的是改造前的工作区基线；已替换内容见第 9 节，不假定源码与已部署版本相同。

- [协调器](../server/v2/coordinator.ts)以 `caseId` 排他，全局两个回合；本机执行在 `handle()` 中等待 `devices.run()`。
- [记忆执行](../server/v2/memory.ts)还有 `caseRuns` 同场景串行队列，任务写入场景 thread。只增加队列或并发数不能解决上下文竞争。
- [任务结构](../shared/task-consent.ts)和[许可校验](../server/v2/consent.ts)把目标与媒体参数、单条命令、精确文件清单绑定；媒体和本机命令各自要求单能力任务。
- [设备操作](../server/devices/broker.ts)仍有一任务一操作的查找/编号假设；媒体已经支持提交后查询原任务，不能再包一层独立调度。

目标仍是一套 Mastra 运行时和一个 [RuntimeApi](../server/runtime.ts)。职责如下：

| 对象 | 唯一负责的事实 | 不承担什么 |
| --- | --- | --- |
| 场景及 scene thread | 交流归属、背景、本人对话历史 | 后台任务的排队锁和完整工具轨迹 |
| 任务 | 委托目标、要求修订、验收要求、执行关联与业务进展 | 在摘要里另存一套许可或凭模型自述宣布成功 |
| 任务许可及资源授权 | 本人允许的目标/操作范围、来源和当前有效版本 | 因任务状态更新、上下文关联或设备在线自动扩大权限 |
| task thread / Mastra run | 一项任务的隔离模型上下文、原生执行检查点 | 原始事件、授权和外部操作回执的替代品 |
| 操作记录 | 一次具体操作的参数、范围快照、外部编号及真实回执 | 凭提交成功认定整项任务已完成 |
| EventInbox、公开消息、个人记忆 | 分别保留原始来源与投递事实、已交付正文、两类有证据的记忆 | 新增一个可写的“全局大脑摘要”作为竞争真源 |

上述职责是现有数据所有权的收敛，不要求为每个概念新建服务或数据库。任务进度由许可、run 和回执按统一转换规则推进；页面是投影。模型工作状态和搜索索引均可重建。

## 3. 保留、替换、删除清单

以下删除项均指替换完成后的可执行路径，不提前删数据；有价值的边界测试随行为迁移。

| 范围与主要文件 | 保留 | 替换与完成后删除 |
| --- | --- | --- |
| `server/runtime.ts`、`server/v2/http.ts`、`shared/runtime-view.ts` | 唯一状态/命令契约及现有 HTTP 入口 | 扩展同一契约；删除直接依赖旧执行形态的内部调用，不新增 `/v3` 并行运行时 |
| `shared/task-consent.ts`、`server/v2/consent.ts` | 来源校验、持久许可、CAS、原子 outbox 和幂等 | 分清要求版本、批准范围和实际操作身份；移除目录查询只能独立任务的限制。媒体/原始程序的进一步组合待真实执行支持，不先放宽schema |
| `server/v2/inputs.ts`、`server/v2/capabilities.ts` | 本人消息身份、请求去重、提案和真实执行隔离 | 明确委托统一登记；替换媒体专用授权分支、目录一律再批准及普通任务必须换入口的限制。媒体参数/目录查询能力适配保留 |
| `server/v2/coordinator.ts`、`server/v2/memory.ts` | 单实例租约、场景聊天顺序、Mastra 模型/工具循环 | 前后台独立额度、任务独立 thread/run；移除任务对场景的双层独占及 `handle()` 内联长任务等待 |
| `server/devices/broker.ts`、`server/media/jobs.ts`、`shared/local-device.ts` | 原生设备/MXC、Hub HTTP、现有操作编号、私有产物及真实回执 | 接入统一提交/查询/取消/结果约定；删除按任务推断唯一操作及各自驱动任务终态的重复入口。Hub 视频串行约束保留 |
| `server/v2/device-results.ts`、`server/v2/run-response.ts`、`server/runtime-stream.ts` | 迟到回执匹配、公开正文持久化、幂等交付 | 任务完成和恢复由同一结果入口收敛；删除重复交付及恢复补偿分支，不另存一份完整工具输出 |
| `server/v2/workspace.ts`、桌面执行端 | 已核验的范围、隔离、工作树身份与验证回执 | 第一轮沿用真实能力；后续在范围检查和执行隔离完成后替换扩展名/精确命令限制，不先删白名单放开任意执行 |
| `server/v2/events.ts`、`sources.ts`、`recall.ts`、连接器 | 原事件、来源代次、观察范围、去重和有效证据回查 | 增加任务/外部对象引用；逐步解除“同场景才是同件事”的硬绑定，保留来源权限检查 |
| `server/v2/personal-memory.ts`、`scene-memory.ts` | 本人理解/方法分离、纠正撤回、原始证据和派生索引 | 接入真实任务结果及本人反馈，方法假设不自动升级为已验证能力 |
| `client/components/Conversation.tsx`、现有任务/设备面板 | 场景及历史、流式正文、当前操作入口 | 展示同一任务的进度/等待/取消/结果；普通委托免重复批准，高影响或越界时才呈现决定点 |

这一轮不增加新外部写入渠道、通用桌面控制、多模型团队、通用插件注册平台或模型 Watchdog。既有读取连接器和能力仍使用现有适配器。

## 4. 委托、权限与任务变更

当前本人消息由已有对话模型理解，登记目标、验收要求和资源范围，并绑定服务端核验的原始消息/事件。清楚委托直接获得该范围许可；讨论、能力询问和自主建议保持提案。无需关键词路由或另一次强制分类模型调用。语义判断本身不等于形式化证明，模型误判要在真实试用中校准。

执行时同时检查三件事：任务是否仍有效、当前要求是否匹配、实际操作是否被有效资源授权及目标覆盖。工具记录准确路径/参数快照；用户可以按项目、目录、文档等表达范围，不必为每次普通调用列文件。新授权表达必须先具备实际执行约束；尚未实现的权限不能靠提示词授予。

| 情况 | 处理 |
| --- | --- |
| 委托内查询资料、可恢复编辑、已有隔离能力支持的普通步骤 | 自动执行；精确参数进入操作记录 |
| 对外动作已由本人明确指定对象和内容范围 | 该委托可构成具体许可；仍受实际已接入能力约束 |
| 新增目标、未开放的目录/账号、超出约定的对外对象 | 暂停相关动作，取得新增范围许可，其他独立交流保持可用 |
| 不可恢复的大量删除、覆盖生产数据、付款/新增付费承诺、扩大账号/设备权限 | 核对针对真实对象和影响的具体许可；不足时先准备可审阅内容，再询问 |
| 自主发现、第三方消息、外部文档中的命令 | 仅作为观察/提案，不创建执行许可 |

模型不能通过自报“低风险”绕过规则；任意 shell 也不能通过关键词黑名单获得可信风险结论。只对实际能力、资源约束和影响可以核验的普通操作自动放行。

区分三个身份：

1. **授权版本**记录允许范围及撤销，不随普通状态变化失效。
2. **要求版本**记录目标内的具体要求变化；本人补充在原范围内直接生效，扩大目标则取得对应许可。旧执行器在下一安全边界停止使用过期要求。结果转换与完成提交同样检查当前要求版本；旧版本的迟到成功保留为真实操作事实，但不能自动满足新要求或将当前任务标为完成。
3. **操作 ID**在调用前持久登记，绑定该次参数和授权/要求快照；状态查询、重启、结果重投使用同一 ID。一个任务可以有多项操作，不能重用一个 ID 承载不同参数。

已被外部受理的操作可能无法改写或撤回，必须说明实际状态。请求取消先阻止新调用，只有原生工具和已接受写入排空后才确认已停止。

## 5. 第一轮：一个闭合的后台任务流程

第一轮验收故事：本人在同一场景明确委托一项现有能力能完成的工作；Rae 登记许可并后台处理，期间本人可以聊天、查看进度、补充范围内要求或取消。断线/重启后仍找到原任务和原操作，已交付的正文保留，结果只交付一次。

具体组合用例：本人明确委托“查询这个目录，再根据结果整理一份清单并保存交付文本”。目录查询与交付各有稳定操作身份，单次查询成功不等于整项任务完成；重复或迟到回执不能跳过整理/交付步骤。以此证明真正替换了单分支执行，不能只放宽 schema 而仍按 `spec.media / spec.command` 二选一。

实施顺序和退出条件：

1. **原生持久执行离线验证。** 用现有 Mock、隔离临时数据和网络保护验证已安装 Mastra 的恢复方式。确定一种持久执行机制；验证不通过先处理已证实的不兼容，不先自造检查点框架。
2. **唯一任务模型和接收入口。** 整理任务/许可/操作归属及版本；通用明确委托、已有媒体和目录委托进入同一登记路径。旧手动表单与提案按钮可保留为 UI 入口，但调用同一命令。
3. **任务独立上下文与调度。** 同时替换 coordinator 的场景占用和 memory 的 task 写入场景 thread。前台保留额度；任务等待外部结果时释放计算槽；实际共享资源有冲突才串行。
4. **已有能力的异步操作与结果交接。** 文件/文本、设备、媒体按真实差异提供薄适配，共用许可检查、结果关联和任务转换。不能在新机制外继续保留一个媒体/设备任务执行器作为后备路径。
5. **迁移、界面和完整验收。** 带旧数据升级，移除内部旧入口及过时行为测试；保留安全性测试并补充新语义。一个切片完成后再发布。

各步骤是第一轮内的依赖顺序，不是五个分别半接通的上线版本。实现可以分提交，发布以闭合切片为单位。第一轮的重启保证限于保留现场、核对原操作及验证过的安全恢复，不宣称任意任务无缝续作。

后续轮次在这条路径上增加：已有来源与同一任务的关联/接续、更完整的安全恢复，以及普通编程/文件操作范围。新增渠道写回按真实需要独立接入，不与第一轮捆绑。

## 6. 框架复用与恢复准入

本地安装的 `@mastra/core` 为 `1.81.0`。已通过[原生 Workflow 离线准入](../tests/mastra-durable.test.ts)，包含独立进程冷恢复、重复恢复拒绝、原权限与步数/期限复核，以及操作受理/文本保存后检查点未提交时的硬退出恢复。最终仅采用原生 Workflow，模型调用继续使用现有 Agent 流式循环和 UsageTracker，没有引入 DurableAgent 第二条执行路径。

已核查的限制要求进入离线用例：

- `agent/types.d.ts` 的 `AgentDurableOption` 说明：默认保存 pending/paused/suspended，running 检查点取决于恢复配置。不能把 `durable: true` 当作完整崩溃恢复保证。
- `agent/durable/durable-agent.d.ts` 对模型实例跨进程恢复有限制；注册 agent、模型包装和执行前授权检查必须重建，不能期待闭包自动恢复。
- 恢复从当前有效连接重新绑定凭证和工具守卫；检查点只保留必要引用和版本，不持久化密钥，也不能把旧许可快照恢复为当前有效授权。
- `agent/durable/types.d.ts` 说明执行超时按 stream/resume/recover 会话重新计时。AR 必须保存并检查原期限、已消耗步数和供应商实际用量；重启或恢复不能自动刷新限额。
- 检查点前后发生工具受理、正文写入或回执提交时，均须故障注入验证。没有外部幂等保证的未知操作只能核查，不自动重做，不承诺通用 exactly-once。

选定后仅保留一种原生持久执行机制。现有事件 outbox 负责可靠投递、操作回执负责外部事实，均不能再驱动另一个模型循环。等待期间不做模型轮询，原有无工具续写、输出保留、token 缺失标记和回合上限继续有效。

## 7. 数据迁移与回滚

2026-11-10 本人明确取消普通工作统一五分钟的默认截止。本人对话、新获准任务和有本人来源的定时回访不再隐含总时长上限；单次请求超时、手动取消和已受理操作排空仍独立生效。本文提到的“原期限保留”适用于历史记录已经保存的有限 deadline，不为它们刷新额度、自动复活或更改旧许可。新的无默认期限记录显式保存 `deadline=null`；恢复仍保留原步数与用量。被动自主回顾继续有界。

- 保留场景 ID、原始消息/图片、个人记忆版本、任务及许可来源、设备/媒体操作编号、实际用量和产物。新 task thread 关联原任务，旧场景历史保留可读，不伪造为过去已经隔离执行。
- 旧批准任务只映射原有精确权限；旧提案不自动批准，旧聊天不重新判读为委托，终态不自动复活，prepared 不升级为已验收。进行中的旧操作先核对/排空，未知状态继续保留。
- 迁移只建立新的结构和关联，保留旧记录及导出。明确 schema 版本与迁移记录；升级中断可恢复。跨库迁移用记录/核对推进，不声称存在跨 SQLite 文件原子事务。
- 升级前暂停新执行并排空已接受操作，备份完整数据目录和原发布快照。`kernel.migration`记录跨组件初始化进度，三轮内核升级完成后的数据版本为3，2026-11-10本人记忆可靠性改造提升为`kernel.schemaVersion=4`；早期migration记录保留在`kernel.migrationHistory`。失败后可在同一版本重开完成迁移，不刷新原授权。当前写入器会拒绝未知的较新内核版本。
- 本次之前发布的旧二进制并不认识该版本标记，因此不支持直接切换旧代码读写升级后的库。发布回滚必须同时恢复对应版本的成套备份，或经过明确验证的兼容迁移；版本标记本身不能让历史二进制自动获得降级保护。
- 回滚须先保全升级后的新增消息、回执与产物，再采用经验证的兼容回退或还原成套备份。无法无损还原时保持暂停和可读/导出，不在新库上强行运行旧执行器。
- 只保留必要的旧数据读取/导出和有退出条件的迁移代码；不能用永久 feature flag、旧队列或旧协议维持两套生产执行链。

## 8. 验收与复杂度约束

实时回执按已受理操作的标识和序号确认。重复上传只核对持久记录。实时进度和结果更新按受影响的任务处理，全量历史核对用于显式导出或启动恢复。改变回执、重连或实时状态入口时，离线回归须覆盖确认丢失后的重复上传、无关历史增长和其他请求仍能响应。以全量读取次数和重复派发次数为断言。

沿用现有测试基础，修改行为断言，不因不再逐次审批而删除来源、范围、撤销和去重保护。

| 必测情形 | 核心断言 | 现有回归基础 |
| --- | --- | --- |
| 明确委托与讨论/外部指令 | 仅真实委托创建许可；普通步骤无二次批准；歧义仍提案 | `task-consent`、`growth-and-consent-flow`、`media-flow` |
| 一任务组合目录查询与文本交付 | 各操作身份稳定；部分成功不完成整任务；重复回执不跳过后续操作 | `local-execution-runtime`、`growth-and-consent-flow`，新增组合任务用例 |
| 同场景后台任务阻塞 | 前台可以处理新消息；两个 thread 不串写；其他任务公平推进 | `v2-fairness`、`v2-memory-race` |
| 补充要求、撤销和停机竞争 | 过期要求不启动新操作；旧版本成功不完成新版本任务；接受的操作排空后才报告停止 | `stabilization-cancellation-barrier`、`stabilization-tool-drain`、`local-execution-runtime`，新增要求变更与迟到回执竞争用例 |
| 调用前/后崩溃与重复回执 | 原操作只查不盲重做；原结果只交付一次；未知保持未知 | `consent-recovery`、`device-result-recovery`、`desktop-result-delivery`、`media-flow` |
| 恢复后模型调用 | 原步数/期限不刷新；模型包装及当前许可重新检查；用量不重复 | `bounded-run`、`stabilization-usage-crash`、`native-usage` |

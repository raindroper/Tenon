# 开源项目标准评审 · 2026-11-08

## 结论与范围

Tenon 已有值得保留的工程基础：单一运行时、持久任务许可、来源追溯、取消排空、故障恢复和大量离线回归。当前更适合定位为面向单用户的早期原型；面向陌生用户公开发行前，仍需补齐项目许可、独立发行配置，并处理实时状态体积和依赖审计问题。

评审起点为 `<revision>`，`package.json` 版本为 `0.1.11`，当时工作区干净。检查覆盖仓库结构、产品契约、HTTP/鉴权、存储、任务准入与执行、来源/连接器、桌面安全与更新、React 状态传输、构建脚本和 CI；对关键路径做源码抽查，并运行现有全量离线测试。它不等同于逐行全量安全审计或真实供应商端到端验收。

评审后半程出现并行的通知功能改动，涉及 `server/store.ts`、`server/v2/coordinator.ts`、公共视图及新通知文件。本次未改动、回退或验收这些代码；下列通过结果属于运行检查时的代码状态，不能视为对后续工作区修改的验证。

优先级：P1 为公开发行前的阻断项或数据安全问题；P2 为应在相应功能推广前解决的问题；P3 为低风险一致性问题。许可证和文档问题与运行时缺陷分别列明，不把所有发布准备项都视为安全漏洞。

## 发现

### F1 · P1 · 缺少项目级许可证，无法确认项目的复用许可

**证据：** 仓库根目录没有 `LICENSE` / `COPYING`；[package.json](../package.json) 没有 `license` 字段。现有许可证仅位于 [desktop/wechat-db](../desktop/wechat-db)，对应被使用的第三方组件。`private: true` 是 npm 发布保护，不是项目许可证。

**影响：** 外部使用者和贡献者无法从仓库确认项目自身适用的许可条件。当前不能把 README 标成已经采用 MIT、Apache-2.0 或其他许可证的项目。

**建议：** 由所有者确定项目许可证及权利归属，补充根 LICENSE 和准确元数据；发行前核对 npm、模型权重及桌面捆绑资源的第三方声明。已有微信 worker 来源及修改声明应保留。

**状态：** 未解决。README 已准确标注许可状态，本次没有替所有者选择许可证。

### F2 · P2 · 自行部署和桌面更新仍绑定维护者实例

**位置：** [desktop/main.ts](../desktop/main.ts) 第 22 行、[desktop/update-manifest.ts](../desktop/update-manifest.ts) 第 6–7 行、[client/lib/desktop-download.ts](../client/lib/desktop-download.ts) 第 3–4 行，以及 [desktop/controller.html](../desktop/controller.html)。

**触发：** 外部用户从源码构建客户端，或部署自己的网页服务，再使用“下载 Windows 客户端”“检查更新”。

**实际行为：** 初始服务地址和网页下载链接固定为维护者域名；更改客户端服务地址后，更新地址和内置签名公钥仍固定。独立发行无法仅通过服务设置切换到自己的发行渠道，可能下载并安装原发行方的程序。

**建议：** 建立一个明确的构建期发行配置，统一服务默认值、下载入口、更新地址和公钥；独立构建在未提供有效发行配置时关闭更新。增加两个不同发行配置的构建/签名回归，验证它们不会跨渠道下载。保持更新验签，不能以禁用校验解决配置问题。

**状态：** 未改代码。README 已说明独立发行限制。这不是已证实的更新签名绕过问题。

### F3 · P2 · 当前场景快照仍携带全部历史资料正文，体积无界增长

**位置：** [server/store.ts](../server/store.ts) 的 `publicDocuments()`（第 123–130 行）、[server/v2/coordinator.ts](../server/v2/coordinator.ts) 的 `snapshot()`，以及 [server/runtime-stream.ts](../server/runtime-stream.ts) 的顶层字段增量传输。

**原因：** 消息、运行和事件已经分页，但 `publicDocuments()` 仍读取并返回所有 `sources` / `artifacts` 的完整正文，`snapshot({ caseId })` 无条件合入这些数据。任务、媒体、反馈集合也仍全量进入状态。缓存减少数据库重复读取，却没有限制序列化与客户端接收体积；顶层增量协议在资料集合改变时仍整体替换该字段。

**离线复现：** 使用全新临时数据，创建当前场景与另一个资料场景；通过 `RuntimeApi.addSource()` 在资料场景添加 100 份、每份 100 KiB 的合成文本；保持推理关闭，读取当前空白场景的 `snapshot()`。

| 指标 | 结果 |
| --- | ---: |
| 添加资料前的 JSON 字节数 | 2,085 |
| 添加资料后的 JSON 字节数 | 10,287,298 |
| 当前场景消息数 | 0 |
| 返回的资料正文数量 | 100 |
| 模型运行数 | 0 |

**影响：** 首次打开、切换场景和 SSE 重连必须传输不相关的历史正文。随着资料积累，网络、JSON 解析和浏览器内存成本持续增加；这与“长期相处”的使用模式直接相关。当前是同一主人的全量数据问题，本次没有将其描述为跨用户泄露。

**建议：** 沿用唯一 `RuntimeApi`，把实时资料/交付列表改为有界摘要，正文按 ID 分页读取；任务和反馈提供有界查询，完整导出继续遍历全部数据。替换旧全量字段的内部调用者，不再新增一套状态真源。回归应同时预置大量资料、成果、任务与反馈，并验证快照大小、切换/重连和完整导出。

**状态：** 已复现，未改运行时。临时复现脚本位于本地忽略目录，通过现有测试启动器运行，测试数据已由启动器清理。

### F4 · P2 · 桌面构建链含受公告影响的 minimatch

**证据：** `npm audit --ignore-scripts --json` 返回 6 个 moderate 依赖节点、0 high、0 critical。它们源于同一条 [GHSA-g3hv-75wg-m249 公告](https://github.com/advisories/GHSA-g3hv-75wg-m249)，不是六项独立漏洞。

[package-lock.json](../package-lock.json) 锁定了 `minimatch@10.2.6` 和 `@electron/universal` 下的 `minimatch@9.0.9`，两者均标为开发依赖，经 `electron-builder` 打包链引入。公告描述特定优化模式下，不可信 glob 模式可能造成 CPU/内存消耗放大；修复版本为 11.0.1。

**影响判断：** 依赖风险已确认；本次没有证明它可由线上 API 或模型输入触发，因此不把整个服务判为可远程利用。应重点评估不可信打包配置、PR 构建和发行环境。

**建议：** 验证兼容的上游打包依赖更新，或在明确兼容性后采用范围受控的修复。审计输出建议的 `electron-builder@24.13.3` 是跨主版本降级，不能直接执行 `npm audit fix --force`。升级后重新验证 Windows 构建、文件清单和更新签名。

**状态：** 未修改依赖或锁文件。当前 CI 不包含依赖审计门禁，可另行补充与风险分级相匹配的检查。

### F5 · P1 · 桌面说明中的旧回滚建议与当前内核契约冲突

**原位置：** [docs/windows-desktop.md](windows-desktop.md) 的“服务更新与回滚”。旧文仅要求回滚代码时保留新增表和日志，没有要求匹配的数据备份或兼容迁移。

**影响：** 该段容易被理解为允许旧二进制直接读写升级库；当前 [内核迁移契约](kernel-upgrade-2026-11-07.md#7-数据迁移与回滚) 已明确，旧二进制不认识新的数据版本标记，不支持这种就地降级。照旧说明操作存在破坏用户数据的风险。

**状态：已修正文档。** 现在明确要求先保全新增历史，再恢复对应版本的成套备份或使用经验证的兼容迁移，并链接唯一的当前契约。本次没有执行备份恢复、迁移或部署。

### F6 · P3 · Windows 启动器仍提示过时的 Node 最低版本

**位置：** [start-local.ps1](../start-local.ps1) 第 3 行。

**触发与结果：** 全新 Windows 环境未安装 Node 时，启动器提示安装“22.13 或更高版本”；实际 `package.json` 和 `with-runtime.mjs` 要求 24.22.1+。按提示安装 Node 22 的新使用者仍无法启动，且源码不提供维护者机器上的本地备用运行时。

**建议：** 对齐启动器提示和版本预检，所有入口说明相同的最低要求。当前 README 已明确 Node 24.22.1+，不再假定外部用户拥有 `.local/runtime/node.exe`。

**状态：** 脚本尚未修改；本次只做评审和文档整理。

### 非阻断改进

- **社区入口：** 补充独立 `CONTRIBUTING.md`、`SECURITY.md` 和实际可用的漏洞私下报告渠道。当前没有可核验的渠道，因此没有编造联系邮箱。公开仓库和历史材料发布前还需要单独做全 Git 历史的凭据/个人信息检查。
- **可维护性：** 协调器、连接器服务与事件模块承担较多职责。后续有行为改动时，沿现有 `RuntimeApi`、许可与生命周期所有权拆分，避免为了减少行数再造框架或第二条执行链。
- **前端体积：** 本次构建主 JavaScript chunk 为 539.15 kB，gzip 167.53 kB；面板已懒加载。可用构建分析定位剩余依赖再按需拆分，不能仅调高告警阈值。尚未测量真实设备的首屏时间。
- **浏览器回归：** 现有客户端状态与 Markdown 测试较充分，但 CI 未配置真实浏览器端到端流程。建议围绕登录失效、消息去重、场景切换、SSE 重连及任务取消建立少量离线闭环测试。
- **运维体验：** 现有 `ops/systemd` 和历史部署材料依赖特定机器，应提供可替换参数的通用部署说明。JSON 导出与完整恢复备份应继续分清；当前 README 已解释二者差异。
- **能力措辞：** 完整资料遗忘、通用电脑操作和自动多模型能力都不能当成已实现功能。README 已明确限制，保留单用户原型定位。
